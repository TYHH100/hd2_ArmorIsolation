# 护甲资源复用能否消除

## 结论

**存在明确的实现路线：按套装建立私有资源 ID，并重写完整引用链。**当前原生代码支持体甲、头盔从 Kit 的 Piece.Path 创建不同 Unit，没有发现“这些套装必须使用同一个 Unit”的固定限制。

但本轮完成的是运行时代码分析、共享统计和离线引用改写验证，**尚未完成游戏内加载与视觉验证，不能当作已可部署的全护甲独立补丁**。

这里的目标是：给某套护甲安装模型、材质或贴图模组时，不影响其他套装的外观。现有角色动画、物理、渲染引擎等公共系统的隔离不包含在资源改名中。

分析对象仍为 `game.dll 1.0.0.18930` / Steam build `24826606`。本次读取 PID `24496`，DLL 哈希及加载模块标识通过核对；未修改游戏文件或内存。

## 1. 复用的真正原因

当前版本引擎按资源类型及资源名称 ID 查找，所查调用没有把套装 Archive 当作额外命名空间：

| 本机原生代码 | 直接证据 |
| --- | --- |
| `helldivers2.exe+0x334330 -> +0x1A8810` | Unit 创建入口 |
| `exe+0x1A889C` | 使用 `unit` 类型哈希 `e0a48d0be9a7453f` |
| `exe+0x1A88C9 -> +0x5F0040` | 传入资源管理器、类型和 Unit 名称 ID，没有 Archive 参数 |
| `exe+0x30E350` | `Material.set_texture` 用 `texture` 类型及纹理 ID 查找 |
| `exe+0x5F0040` | 先匹配类型，再在该类型中匹配 64 位名称 ID |

所以，将内容中相同的 Unit ID 放进不同补丁包，不能让它们在同一资源管理器内成为两个独立资源。复制或重命名 `.patch` 文件、调整补丁顺序，都不能从根源上解决这个身份冲突。

同样，创建两个不同 Unit 实例只说明两个角色部件有各自的实例状态，不代表它们读取的模型、材质、纹理源资源已经独立。

证据：[本机资源查找反汇编](armor-isolation-resource-lookup.txt)。

## 2. 当前版本的共享规模

本轮读取全部 402 条运行时 Kit，而非只使用社区数据。统计按每套装去重，排除空 ID：

| 范围 | 独立 Unit ID | 被多套装引用的 Unit ID | 涉及套装数 |
| --- | ---: | ---: | ---: |
| 132 条体甲记录，包含默认披风部件 | 1,759 | 420 | 132 |
| 体甲记录，排除 Slot1 披风 | 1,757 | 418 | 99 |
| 155 条头盔记录 | 113 | 12 | 58 |
| 全部 402 条装备记录 | 1,871 | 431 | 195 |

体甲直接引用的纹理资源中还有 **44 个共享 ID，涉及 117 条套装记录**。这尚未计入 Unit 内部材质引用和材质默认纹理的完整依赖。

132 条体甲对应 131 个 Archive。`62c6fbc5cd90448d` 同时对应 Kit `6b619174` 和 `100a5dcd`，所以独立化的归属键应该是 **Kit ID**，不能只按 Archive 分组。

这些是当前配置记录及引用关系数量，不等于商店可购买数量。完整统计：[armor-isolation-summary.json](armor-isolation-summary.json)。

## 3. 正确的独立化结构

```text
当前：
  护甲 A ─┐
          ├─ Unit U ─ Material M ─ Texture T
  护甲 B ─┘

独立后：
  护甲 A ─ Unit U_A ─ Material M_A ─ Texture T_A
  护甲 B ─ Unit U_B ─ Material M_B ─ Texture T_B

Piece 自身的 LUT / 图案 / 贴花引用也分别改成 A、B 的私有资源。
```

至少需要同时完成：

1. 为 `(Kit ID, 资源类型, 原资源 ID)` 分配稳定的新 ID。同一套内部重复引用同一资源时复用该私有 ID。
2. 复制 Unit 的主数据及其实际依赖的 stream / GPU 数据，正确登记新资源 ID 和三路数据位置。
3. 改写目标 Kit 中的 Piece.Path，指向新的 Unit ID。
4. 改写 Unit 的材质资源引用，必要时递归复制基础材质及其他外部依赖。
5. 改写 Material 默认纹理引用，以及 Piece 动态覆盖的 LUT、图案、贴花等引用。
6. 确保新资源和完整依赖在装配之前已加载，并随正确的资源包保持有效生命周期。

仅完成第 3 步会引用一个尚不存在的资源；仅完成第 2 步，新资源不会自动被套装选中；只分离 Unit、不分离被修改的材质和贴图，仍可能联动。

应保留装备身份 Kit.Id、被动、Slot、Type、体型和部件数量。目标是改变外观资源引用，不是新增装备、改变解锁状态或修改护甲属性。

## 4. 单个真实资源的结构验证

以被 27 个 Kit 引用的左臂内衬 Unit `f6d665ef313b5a3c` 为样本：

- 主数据 15,776 字节，GPU 数据 524,672 字节。
- Unit 内的材料表偏移为 `0x3D60`，包含 3 个材料槽及 3 个材质资源 ID。
- 其中两个材质能在所查护甲包中读取，各有 12 条纹理用途记录。
- 第三个材质、两个基础材质不在所查护甲包和基础包中，本轮尚未继续完成它们的跨包定位。这不能解释成游戏资源缺失。

在分析进程自己的内存里，已经为 B-01 和 B-24 建立两份候选结构，分别改写 Unit→Material、Material→BaseMaterial/Texture 的 64 位引用，并验证：

- 资源长度保持一致。
- 材质槽、纹理用途、参数数据和骨骼等非引用字节保持一致。
- 两套使用不同的私有 Unit/Material ID。

这证明已识别字段可以定点改写，不代表完整依赖已经克隆或引擎已经接受新包。未生成或安装游戏资源副本。

例如同一源 Unit 的候选 ID：

| 套装 | Kit ID | 原 Unit | 候选私有 Unit |
| --- | --- | --- | --- |
| B-01 变体1 | `61b31723` | `f6d665ef313b5a3c` | `b638ae8b3954d589` |
| B-24 | `8b9ed77d` | `f6d665ef313b5a3c` | `7730028a5c3a0228` |

这些 ID 只是离线规划结果，目前不在游戏中注册。

字段格式和来源见 [依赖结构笔记](armor-isolation-dependencies.md)，本地样本证据见 [依赖改写验证](armor-isolation-dependency-sample.json)。

### 哪些字段不能盲目替换

Unit 材料表的 32 位 key 是材料槽哈希，64 位 value 才是材料资源 ID。Material 纹理表同样是用途 key 与资源 value 分开。

材料槽名、纹理用途、shader 参数用途、骨骼名哈希、局部索引不是私有资源 ID，不能全文件搜索数字后统一替换。`BaseMaterial` 本身仍是 `material` 类型资源，需要作为依赖处理，不能误当成一个任意 shader 标识。

另有预览头盔路径会读取 `Piece.Path >> 32` 并用于后续材质接口。本轮候选 ID 同时避免了已知范围内的完整 ID 和高 32 位碰撞，但尚未完成全游戏碰撞核对或确定该接口的全部语义。

## 5. 统一修改配置能覆盖哪些路径

| 执行路径 | 创建时读 Piece.Path | 结论 |
| --- | --- | --- |
| 场景体甲 `game+0x8164B0` | 是，创建点 `0x816840` | 集中改引用可覆盖 |
| 场景头盔 `0x8157E0` | 是，创建点 `0x815A66` | 集中改引用可覆盖 |
| 预览体甲 `0x10F62F0` | 是，创建点 `0x10F64D4` | 集中改引用可覆盖 |
| 预览头盔 `0x10F5E70` | 是，创建点 `0x10F5F89` | 集中改引用可覆盖 |
| 场景披风 `0x815DA0` | 使用已经存在的 Slot1 Unit | 只改所选披风 Path 不够 |
| 预览披风 `0x10F60B0` | 同样使用已有 Unit | 同上 |

### 披风要分两种目标

**按体甲隔离默认披风模型：**给体甲 Kit 中的 Slot1 Path 分配私有 Unit，可以被现有体甲创建流程读取。

**每件可选披风也拥有独立模型：**现有流程先由体甲创建披风 Unit，后用所选披风描述设置材质。要让披风选择真正决定模型，需调整场景和预览的披风创建/重建规则。对原本没有模型引用的披风条目，还要明确其默认几何来源。

因此不能只改 402 条 Kit 的资源 ID，就宣称所有装备的模型选择行为都已独立。

## 6. 落地方案与尚未验证的环节

建议采用“资源转换器 + 配置引用适配”的结构，先保留原 Kit.Id 和装备逻辑。

**资源转换器：**按套装读取原始资源和分配给该套装的 Mod，建立依赖关系后生成私有资源及引用映射。必须在不同 Mod 的同名资源合并之前划分归属；如果先让两个 Mod 在全局旧 ID 上互相覆盖，再复制最终结果，原始差异已经丢失。

**配置适配：**在套装表加载完成、相关外观首次创建之前，让目标 Kit 使用私有资源引用。当前代码证明这是有效的消费入口，但本轮没有实施运行时写入。介入时序、配置重载恢复和现有 Unit 重建仍需验证。

磁盘 `.dl_bin` 方案则需要正确重建本版本的受保护容器；读取到了明文运行时结构，并不等于已有可用的磁盘配置编辑器。普通资源补丁也不会自动改写外部 `generated_customization_armor_sets.dl_bin`。

### 包加载不能遗漏

如果私有资源确实能够随原 Archive 可靠加载，可以保留 Kit.Archive。若另建资源包，则必须处理它的加载、就绪检查和持有关系。只改 Piece.Path 不会让引擎自动请求该新包。

仍需实测任意新资源 ID 的目录登记、依赖加载、主数据/stream/GPU 三路偏移和包生命周期。本轮没有生成加载测试包，也没有执行新资源创建。

### 旧 Mod 需要转换

原有 Mod 仍覆盖旧 ID，而独立后的套装已经引用新 ID；旧 Mod 因此需要转换到指定 Kit 的命名空间。单个旧补丁使用共享 ID 时，无法总是从资源 ID 唯一推断作者想替换哪套护甲，需要明确目标套装或可靠元数据。

只按 `(类型, 原 ID)` 做一张全局改名表仍会共享；转换表必须包含 Kit 归属。后续游戏更新还需要重建依赖和重新校验，不能无条件沿用本次偏移或资产布局。

## 7. 本轮离线规划达到的边界

工具 [plan_armor_isolation.py](../tools/plan_armor_isolation.py) 对本版本进行只读采集和 ID 规划：

- 402 条装备的直接引用生成 5,206 个 `(Kit, 类型, 源资源)` 映射。
- 在分析进程的副本中改写 9,682 个直接引用字段，验证该直接引用图的跨 Kit 共用 ID 为 0。
- 若仅按体甲直接引用计算，私有 Unit 需要 3,096 个；原本不同 Unit 是 1,759 个，差额 1,337。
- 同一套内部重复引用同一资源仍复用同一个私有 ID。
- 排除空引用；候选 ID 在本轮直接资源集合和新 ID 集合内检查完整 ID 及高32位碰撞。

**这不是 5,206 个已生成或已加载的游戏资源。**计划尚未包含完整 Unit→Material→Texture/BaseMaterial 等依赖，也未检查全游戏所有名称的碰撞。不能根据该计数直接估算磁盘、显存或运行时内存增长；Slim 存储去重、压缩和新包布局也会影响成本。

原始记录：[运行时套装](armor-isolation-live-kits.json)；候选映射：[ID 计划](armor-isolation-id-plan.json)；校验结果：[统计摘要](armor-isolation-summary.json)。

## 8. 下一步最小验证

先用 B-01 与 B-24 的同一个共享左臂部件验证完整链，再推广到全部护甲：

1. 定位该部件的全部依赖，生成两个不同 ID 的完整资源副本。
2. 为两套各分配一个可辨别的外观变化，转换各自资源引用。
3. 验证新 ID 能在正确资源包加载后被创建，并接入对应 Kit。
4. 检查 A 变化不影响 B，B 变化不影响 A；交换加载顺序后结果仍稳定。
5. 检查两种体型、界面预览、舰桥和任务场景；单独换头盔/披风后保持正确，卸载重启后恢复原样。

这一验证通过后，才有依据扩展到全量转换、旧 Mod 兼容和披风模型规则。当前结论是**代码结构支持实现护甲资源隔离，但尚未验证可部署实现**。
