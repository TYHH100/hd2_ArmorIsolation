# 护甲外观在当前游戏代码中的执行流程

日期：2026-09-19。目标：本机 Helldivers 2，Steam build `24826606`，`game.dll 1.0.0.18930`。

后续资源复用分析见 [护甲资源独立化可行性](armor-resource-isolation.md)。

本次已读取运行中的游戏代码，确认了配置加载、资源就绪检查、外观状态更新、场景护甲装配、材质覆盖和界面预览的主要路径。护甲外观由原生代码组装多个 Unit，相关执行逻辑不只是替换一个模型文件。

## 1. 证据与地址约定

- 进程：本次读取 PID `24496`，安装路径与用户指定目录一致。
- `game.dll` 当次加载基址：`0x7FFB3D320000`；PE 时间戳：`0x6A86132E`；映像大小：`0x3A6B000`。
- DLL SHA-256：`cc75948d90fdfde259dcb519e9933db7ffa3ccb281ce4fb89e6b1b011557470c`，结束前复核未变。
- 下文未注明模块的代码地址均为 **game.dll RVA**；结构体 `+偏移` 和 Unit 文件内部偏移另行标明。
- `ApplyArmor` 等可读名称是本文根据指令行为给出的分析名称，不是恢复出来的原始 C++ 符号。
- 证据来自加载后代码的反汇编和少量数据读取。未设断点、未挂钩、未执行远程函数、未写入游戏内存；不声称所有分支都在本次换装中动态执行过。

## 2. 已确认的原生主干

```text
配置初始化：0x8695D0
  读取 generated_customization_armor_sets.dl_bin
  建立 Kit / Body / Piece 运行时结构

场景外观更新：0x86AF90
  -> 0x86A730：比较期望状态与已应用状态
     -> 0x86FEC0：检查新资源包是否就绪
     -> 0x86DB90：将已应用外观分发给角色
        -> 0x8157E0：头盔路径
        -> 0x8164B0：身体护甲装配主路径
           -> 清理旧 Slot 1..9 的三类部件
           -> 查找 Kit，选择当前体型和通用体型的 Piece
           -> 创建 Unit
           -> 0x815470：链接至角色
           -> 遍历 Mesh / Material，覆盖纹理及参数
           -> 按 Type + Slot 保存新 Unit 句柄
           -> 0x811740：内衬部件的材质遮罩
        -> 0x815DA0：披风配置路径
```

直接调用证据：`0x86AFD8 -> 0x86A730`、`0x86AE1A -> 0x86DB90`、`0x86DEB2 -> 0x8164B0`、`0x816852 -> 0x815470`。还发现另一处调用点 `0x813663 -> 0x86DB90`；本轮不将外观应用限定为某一个界面事件。

来源：[状态更新反汇编](appearance-native-customization.txt)、[场景装配反汇编](appearance-world-native.txt)、[调用点](appearance-native-apply-callers.txt)。

## 3. 配置怎样进入代码

`0x8695D0` 通过引擎文件接口读取配置、调用数据处理函数，检查 `LDLD` 记录头，并调用 `0xA9D0B0` 处理记录内部引用。随后建立 Kit 指针表。`0x86998B` 开始遍历 Body 和 Piece，Body 步长 `0x18`，Piece 步长 `0x60`。

运行时全局入口为 `*(game.dll + 0x276C220)`。其 `+0x00` 是 Kit 指针数组，`+0x08` 是数量。本次实际读到 **402 条：132 护甲、155 头盔、115 披风**。这是运行时表记录数，不是玩家已拥有或当前可购买的数量。

已经直接读取本机运行时的 B-01、SC-34 两条套装及部件，保存于 [appearance-live-kits.json](appearance-live-kits.json)。这部分补足了上一轮仅有社区快照的证据。

### 运行时结构的关键字段

| 结构与偏移 | 内容 | 当前代码证据 |
| --- | --- | --- |
| Kit `+0x00` | 32 位套装 ID | 装配函数据此查找 Kit |
| Kit `+0x20` | 64 位 Archive 标识 | 外观状态更新读取并检查资源就绪 |
| Kit `+0x30 / +0x38` | Body 数组指针 / 数量 | `0xF39010`、`0x816749` |
| Body `+0x00` | 体型 | 等于当前体型或 3 时纳入 |
| Body `+0x08 / +0x10` | Piece 数组指针 / 数量 | 每条 Piece 间隔 `0x60` 字节 |
| Piece `+0x00` | Unit 资源 ID | 创建部件时传给引擎 |
| Piece `+0x08` | Slot：部位 | 作为最终句柄数组索引 |
| Piece `+0x0C` | Type：护甲片、内衬、附件 | 决定写入哪组句柄数组 |
| Piece `+0x10` | Weight | 本次确认的 `0x8164B0` 装配流程没有读取它 |

Slot 对应：`0 头盔、1 披风、2 躯干、3 髋部、4 左腿、5 右腿、6 左臂、7 右臂、8 左肩、9 右肩`。这些名称由社区结构辅助命名，数值的读写、筛选及索引行为已与本版本代码对应。

体型筛选函数 `0xF39010` 可重建为：

```cpp
// 分析伪代码；不是原始函数名或原始源码。
uint32_t CollectPieces(Kit* kit, uint32_t bodyType,
                       uint32_t capacity, Piece** out) {
    uint32_t count = 0;
    for (Body& body : kit->bodies) {
        if (body.type != bodyType && body.type != 3)
            continue;
        for (Piece& piece : body.pieces) {
            if (count == capacity)
                return count;
            out[count++] = &piece;
        }
    }
    return count;
}
```

场景护甲构建函数内联了相同逻辑，容量为 **20**。本机 B-01 配置有通用组 7 条、壮硕组 8 条、精瘦组 8 条；选择任一已知体型得到 15 条，而不是把 23 条全装上。

来源：[配置加载](appearance-native-loader.txt)、[体型筛选](appearance-native-piece-selection.txt)、[社区字段定义](https://github.com/xypwn/filediver/blob/70f3447cd415c964e0bd29ff0770b97a4d0f160d/datalibrary/armor_sets.go)。

## 4. 为什么换装要等待资源

`0x86A730` 同时维护期望状态和已应用状态。以全局对象 `S` 和条目索引 `i` 表示，观察到：

| 内容 | 结构位置 |
| --- | --- |
| 期望外观记录 | `S + 0xA7C + i * 0x40` |
| 已应用外观记录 | `S + 0x96C + i * 0x44` |
| 体型、头盔、披风、护甲 | 上述记录的 `+0、+4、+8、+0xC` |
| 待重建标记 | 已应用记录的 `+0x29` |

套装 ID 改变时先查出新旧 Kit 的 Archive，交给 `0x86FEC0`。该函数检查新包是否就绪；未就绪时检查是否已经在加载队列，必要时调用资源管理函数，并返回 false。调用者据此保留旧套装字段，不立即应用新值。

两个引擎查询接口的实际目标在 `helldivers2.exe`：

- `exe+0x320540`：检查资源包是否在队列中；这是查询，不能把它叫作“发起加载”。
- `exe+0x320600`：检查包存在、相关状态满足条件且已不在队列中，返回就绪结果。

就绪后，代码还通过 `0x105CAE0`、`0x105CC70` 管理新旧包的请求或持有关系。这两个函数的全部引用计数语义未在本轮还原，不能把其中一个调用简单解释为立即卸载。

发生已接受的外观变化时设置待重建标记。角色可解析且标记存在时，`0x86AE1A` 调用 `0x86DB90`，返回后清除标记。由此可见，这是一条状态驱动的装配流程，不是每帧无条件重建全部护甲。

来源：[资源就绪代码](appearance-native-resource-ready.txt)、[期望与已应用状态](appearance-native-customization.txt)、[同版本引擎实现](appearance-engine-api-native.txt)。

## 5. 场景护甲具体怎样装配

主函数为 `0x8164B0`，代码跨多个异常展开片段，延续至 `0x817322`。

### 5.1 清理旧部件

`0x816541` 开始检查三组旧 Unit 句柄数组，处理 Slot 1..9。对于存在且有效的 Unit，调用引擎清理接口并把句柄清零。Slot0 头盔由另一条路径处理。

这三组数组后来分别承接 `Type=0` 护甲片、`Type=1` 内衬以及其他类型附件。因此，同一个身体部位可以同时具有多层部件。

### 5.2 创建和链接

找到 Kit 并完成体型筛选后，循环读取 Piece.Path；资源 ID 为 0 时跳过。`0x816840` 调用引擎创建接口，返回新 Unit 句柄。

`0x816852` 随即调用 `0x815470`，把新部件与角色关联。辅助函数在 `0x8154A6` 传入 world、child、parent 和节点参数，调用引擎链接接口；后续还有局部变换及条件状态设置。这里确认了调用参数和先后关系，未把所有引擎间接接口都恢复为原始 API 名称。

必须区分“链接为角色部件”和“每根骨骼怎样同步”：前者已由原生调用和参数确认；后者还涉及引擎、动画及蒙皮，不是仅凭 link 调用就全部证明。

### 5.3 披风的特殊处理

`0x816906` 检查的是 **Slot1 披风**。某些条件下，会按另一个选定 Kit 查出同体型的披风 Piece，并替换后续使用的描述指针。

这一分支发生在创建 Unit 之后，没有在替换描述时再次创建模型。后续材质等操作使用替换后的描述。因此代码允许“套装提供部件模型，单独选定的披风提供后续外观参数”。这不能扩大为“所有披风永远共用同一模型”。

本机 B-01 和 SC-34 的套装记录都带有默认披风 Path `3c33cf10a26cbb3e`，其披风 LUT 等字段为 0，与这种分工一致。

### 5.4 材质绑定

`0x816B40` 附近开始遍历新 Unit 的 Mesh，再遍历各 Mesh 的 Material。对于非零纹理资源 ID，执行：

```cpp
// 对每个部件的每个材质执行；字段名辅助取自数据结构。
if (piece.materialLut != 0)
    MaterialSetTexture(material, 0x7E662968, piece.materialLut);
// 其余六个纹理字段按相同模式处理。
```

实际场景和预览的材质代码存在相同的七组绑定：

| Piece 偏移 | 配置字段名 | 材质槽哈希 | 哈希校验后的参数名 |
| --- | --- | --- | --- |
| `+0x18` | MaterialLut | `0x7E662968` | `material_lut` |
| `+0x20` | PatternLut | `0x81D4C49D` | `pattern_lut` |
| `+0x28` | CapeLut | `0x0E494183` | `cape_lut` |
| `+0x48` | BaseData | `0xC2EB8D6E` | `base_data` |
| `+0x30` | CapeGradient | `0x8D28873D` | `cape_gradient` |
| `+0x40` | DecalScalarFields | `0x11761ABE` | 未确定 |
| `+0x50` | DecalSheet | `0x632A8B80` | `decal_sheet` |

`MaterialSetTexture` 不是只凭参数猜测：本版本引擎的 Lua 注册字符串 `Material.set_texture` 对应 wrapper `exe+0x49F690`，其中 `exe+0x49F7AA` 调用 `exe+0x30E350`；护甲使用的间接接口也指向 `exe+0x30E350`。

字段名和 shader 参数名不保证一致。例如 `+0x40` 虽在社区解析器中称为 DecalScalarFields，不能未经哈希校验就把目标槽叫作 `decal_scalar_fields`。

场景侧 `0x816AE0`、预览侧 `0x10F3F38` 都先检查上述七项。**七项全零就跳过整段覆盖**，后面的色调设置也不会单独触发。

进入覆盖分支后：

- `Piece+0x58` 不为零时，以玩家相关整数对该值取余，转为浮点写入材质参数 `0x575F7F6E`，其哈希对应 `tone_variation`。这不是观察到的每帧随机取值。
- 随后给材质参数 `0x205E89CC` 写入 0。
- 本段没有读取 Piece 的 `+0x38 CapeNac`，不能声称结构中的每个纹理字段都会由这一函数应用。

### 5.5 保存句柄及内衬遮罩

`0x817255` 读取最终 Piece 的 Type、Slot，把新 Unit 句柄写入对应类型数组的对应部位。内衬还执行 `0x811740`：髋部和躯干使用分别传入的遮罩，其余分支使用 1。

`0x811740` 将遮罩按位取反，再遍历材质，把结果作为两个 32 位元素传给参数 `0xCB029DF0`。这是已确认的材质数据操作；具体哪些像素或区域被遮挡，还要结合该材质着色器解释。

因此“内搭缺失、穿模、局部消失”除了几何问题，还应检查部件类型、槽位、材质参数和遮罩。

来源：[场景构建、链接、遮罩完整反汇编](appearance-world-native.txt)、[预览与材质代码](appearance-material-native.txt)、[API 与参数校验摘要](appearance-material-api-notes.txt)、[同版本引擎注册证据](appearance-engine-api-native.txt)。

## 6. 界面预览与实战场景分开

当前 DLL 的 `testament.MenuTabViewArmor` 类型包含：

| UI 属性 | getter RVA | setter RVA | 字段 |
| --- | --- | --- | --- |
| PreviewArmor | `0x1298A00` | `0x1298A10` | `this+0x168` |
| EquippedArmor | `0x1298AB0` | `0x1298AC0` | `this+0x170` |

`0x1298B94` 注册属性；setter 处理新旧对象引用、替换指针，再经属性名标识发出通知。这些字段保存的是 UI 对象指针，不能将其当作角色 Unit 句柄。

本轮未找到两个 setter 与点击事件、三维预览之间完整的调用来源，故主干图没有假造这条连接。

独立的预览构建代码已确认：

- `0x10F5E70`：过滤 Slot0，处理头盔部件。
- `0x10F62F0`：清理 Slot1..9、按体型选择护甲部件、创建和链接 Unit。
- `0x10F3D40`：预览部件清理。
- `0x10F3F30`：预览材质设置，与场景侧七组纹理绑定一致。
- `0x10F60B0`：过滤 Slot1，为已有披风部件应用配置。

所以“军械库预览正常”只能证明预览分支工作，仍需要分别验证舰桥和任务中的场景外观。此结论来自独立实现路径，不是假设两个场景一定出错。

来源：[UI 属性代码](appearance-ui-native.txt)、[预览构建](appearance-native-build.txt)。

## 7. Unit 创建后怎样参与绘制

本机共享左臂内衬 Unit `f6d665ef313b5a3c` 已解析，资源主数据 SHA-256 为 `2201086fbce314d26f80b061c2332417e503d7c16b884a04debb04c77e2e2bd7`。

- 38 个场景节点，包含左肩、肘、手、手指和网格分组。
- 5 组骨骼映射记录，分别含 25、23、23、23、16 个 palette 项；不能把“5 组”直接理解为5档普通距离LOD。
- 2 条顶点流，GPU 数据大小 524,672 字节。
- LOD0：3,198 个不同顶点，两段索引数分别 15,246 和 2,088，共 5,778 个三角形。两段共享顶点范围，不能把顶点数相加成 6,396。

骨索引关系按资源表为：

```text
顶点 bone_index
  -> 该 section 对应 remap
  -> 骨骼 palette 索引
  -> RealIndices
  -> 场景节点
```

这说明改模型时只保持骨骼名字不一定够，还要保持 section、remap 和 palette 的一致性。资源证据见 [appearance-assets.json](appearance-assets.json)。

本轮没有反编译最终 GPU shader，也没有完整追踪每帧动画矩阵、布料求解、LOD选取和绘制提交；这部分是资源结构说明，不能写成已经恢复的完整渲染器实现。

## 8. 已确定与仍未知

已确定：当前版本存在原生状态更新、资源等待、按体型装配、多类部件槽、逐材质纹理覆盖、披风描述替换及独立预览路径。模型共用造成外观联动，也能在“不同套装 Path 指向同一 Unit”的配置关系上解释。

仍未知：UI点击到期望状态写入的完整事件链、所有引擎接口实名、骨骼同步细节、最终shader如何消费全部参数，以及网络中外观状态的同步协议。

本轮没有改动游戏、部署补丁或复制 DLL。保存的是中文说明、必要的反汇编文本和少量结构化资源证据。
