# TG-122 模块化模组参考

分析日期：2026-09-19。样本：`1/milltina 修女 替换tg-122/`。

后续实现已完成，当前工具行为见[保留选项目录的隔离生成](modular-isolation-tool.md)。本文保留当时的只读分析及设计推导，下面的“尚未实现”描述属于该次分析时点。

用户提供此模组作为配件开关和外挂材质包的参考，并说明它没有污染。本轮只读分析源补丁、manifest 和对应游戏资源，不对样本做隔离转换，不部署游戏，也不将它列为需要修复的污染样本。

## 配件和互斥选项

五个配件分别覆盖本体中的一对 Unit，对应 Body.Type 0、1；五组之间没有重复 Unit ID。

| 配件 | Slot / Piece.Type | Body 0 Unit | Body 1 Unit |
| --- | --- | --- | --- |
| 内裤 | 8 / 0 | `cae8a5358d93434b` | `cb4a83f595d19f43` |
| 内裤链珠 | 3 / 0 | `4af7e6656da96318` | `29a22cece5427d2d` |
| 翅膀 | 9 / 0 | `5b9e622f3d345bc2` | `7ed0d83aea809fcd` |
| 胸衣 | 2 / 0 | `6b826d06ab7af07c` | `4249a344a5268033` |
| 腰裙 | 3 / 1 | `b493847e2d29b52d` | `8ae533a9529a8b11` |

这 10 个 Unit 的 main 和 GPU 数据均与本体同 ID 版本不同，已对有效段散列核对。本体对应 GPU 段仅 822 至 950 字节，配件版本达到数 MB，支持“本体保留小型占位模型，配件提供几何覆盖”的解释。具体哪个部件显示或隐藏仍以游戏画面为准，不能只凭文件夹名称断言。

头部三个版本共同使用 `e79251f8f34d351a`，Body.Type 3、Slot 0、Piece.Type 0。默认版本在本体中，GPU 有效段为 22,143,080 字节；“去头盖”和“去长发”是两个 main/GPU 都不同的完整替代版本。同时加载两个版本不能表达“同时去头盖并去长发”。

manifest 的 `Options` 表示可开关组件，`SubOptions` 表示父组件内选一个子项。清单声明 `头/默认`，本样本实际没有此目录，效果可解释为不添加头部覆盖；通用导入时必须显示这一缺目录状态，不能把任意缺失文件都自动当作合法默认。

本地管理器 `ModService.Deploy.cs` 的 `AddFilesFromDir` 使用非递归 `GetFiles()`；部署收集父项 Include 和被选中子项 Include。递归扫描 `头/` 会错误收集两个互斥补丁。manifest 也不保存本次实际勾选状态，不能由清单推断用户已启用了哪些配件。

## 跨补丁依赖和复用

在内存中模拟有效资源表：以本体与材质包为基础，对选定配件使用其 Unit 版本，头部使用默认或一个替代版本。该模拟明确指定每个资源的来源，未验证游戏自身的补丁覆盖优先级，也没有写出合并补丁。

| 有效目标 | Unit | Material | Texture |
| --- | ---: | ---: | ---: |
| 体甲，五配件全关或全开 | 22 | 6 | 22 |
| 默认头盔 | 1 | 5 | 15 |
| 去长发头盔 | 1 | 5 | 15 |
| 去头盖头盔 | 1 | 2 | 6 |
| 体甲 + 任一头部版本，依赖并集 | 23 | 8 | 28 |

材质包可在模组内共享一份。直接把体甲闭包与头盔闭包相加会重复复制共同依赖；为每个配件另复制整套贴图更没有必要。五个独立开关与三个头部选择在结构上有 96 种组合，本轮没有逐一进行游戏测试。

本体加材质包的 GPU 有效段总和为 465,250,746 字节；五配件全开且默认头部时为 516,730,622 字节。这是选定有效资源的数据量，不是已生成补丁的文件大小，实际重打包还需计算对齐。

外部原版依赖仅在上述两个目标 Archive，以及 `9ba626afa44a3aa3`、`18235e0c9ec0e636` 内核对：16 个外部 Material/BaseMaterial 均可定位，没有指回本模组修改纹理或基材质的交集。外部纹理共 52 个，其中 50 个在该范围定位；`12d4692531c1fd35`、`eb86d298e6cc8f94` 未在此范围定位，不等于游戏中缺失，本轮未扩大扫描。

## 通用工具应如何扩展

以下为设计约束，尚未实现多补丁生成：

1. 导入一个模组的组件集合，保留 manifest 的父子关系、启用状态和子项选择。先确定有效资源来源，再分析目标；不默认启用全部目录。
2. 索引用 `(资源类型, 原 ID)`，记录每条资源来自哪个补丁及其 main/stream/GPU 三路偏移。同 ID 不代表内容相同，覆盖必须替换完整资源三路来源。
3. 用显式选择决定覆盖版本，并保留覆盖记录。不能把目录排序、同名 `patch_0` 或 manifest 顺序当作已验证的游戏优先级；无法确定的冲突应在生成前解决。
4. 跨组件追踪 `Unit -> Material -> BaseMaterial/Texture`，本体和外挂材质包共同构成输入。材质/纹理按模组共享私有 ID，Unit 按 Kit 隔离。只输入材质包仍不等于支持纯贴图隔离。
5. 若输出保留管理器配件开关，应先为整个组件集合建立一致的私有 ID 映射；本体 Unit 和对应配件 Unit 使用相同私有目标 ID，分别保存在基础补丁和可选覆盖补丁中，共享材质包只保存一份。不能将每个组件当成独立模组分别分配 ID。
6. 同一目标 Kit 始终只有一份有效运行时配置。当前通用插件会拒绝多个 JSON 同时声明同一 Kit；配件不各自输出一份争用 Kit 的 JSON。选择不同组合时，生成/部署层计算当前需要的资源集合，只等待启用组件实际需要的资源。
7. 切换组合需要与补丁部署和 JSON 更新一并完成，并完整重启游戏。现有插件不热加载配置，也不在运行中恢复已发布指针。

可先实现“明确选择组合后生成一套有效资源”的阶段，再保留可开关的分层输出；第一阶段的合成包不具备安装后独立切换配件的能力，不能称其已完整支持作者的组件结构。组件映射稳定性、选择记录、共享包和输出层次需要单独验证。

当前 ReShade 插件已按资源 ID 和每 Kit 依赖工作，不依赖资源原来存在哪个补丁。结构上可继续使用同一个 DLL；新增工作集中在离线组件选择、来源索引、依赖分析和打包。该结论不是此样本已经通过通用隔离后的游戏验收。
